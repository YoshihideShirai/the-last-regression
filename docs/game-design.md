# デバッグ裁判：最後のリグレッション 設計ドキュメント

このドキュメントは、ゲームの**ストーリー**と**システム仕様**を整理したものです。  
実装 (`src/main.ts`, `src/gameLogic.ts`) と合わせて、企画・開発・テスト時の参照用として利用します。

---

## 1. ゲーム概要

- ジャンル: 会話選択式ミステリー / デバッグ推理
- テーマ: ソフトウェア開発現場で発生したリグレッションの真相究明
- プレイヤー役: 「超高校級デバッガー」
- ゴール: 証拠（コトダマ）を集め、最終議論で正しい原因を論破する

---

## 2. ストーリー

### 2.1 導入

リリース直前、`checkout` 機能がクラッシュし、CI が赤に変わる。  
チームは混乱し、誰の変更が原因か分からない。  
プレイヤーは証言とログを突き合わせ、バグの根本原因を特定する。

### 2.2 チャプター構成

#### チャプター1: 初動調査

- 状況: 本番相当環境で `checkout` がクラッシュ
- 主な選択:
  - CIログを精査する（有効）
  - 全員を疑う（非効率）
- 取得可能証拠:
  - `log`（`payment.total` が `undefined`）

#### チャプター2: 証言とPR分析

- 状況: 3人の開発者証言を比較
- 主な選択:
  - PRとdiffを確認する（有効）
  - 勘で特定人物を追及（非効率）
- 取得可能証拠:
  - `pr`（金額計算共通化PR）
  - `test`（`checkout` のみ fail）

#### チャプター3: 仕様照合

- 状況: 仕様書と実装ロジックの整合を確認
- 主な選択:
  - 仕様書を確認して証拠化（有効）
  - 勢いでhotfixを入れる（証拠不足リスク）
- 取得可能証拠:
  - `spec`（税計算後は `roundUp` 必須）

### 2.3 最終議論（裁判）

プレイヤーは犯人候補（原因仮説）を選択する。

- 不正解候補:
  - 在庫API遅延説
  - CSS改修説
- 正解候補:
  - 金額計算の共通化で `roundUp` が `round` 化され、`total` 返却漏れを起こした説

### 2.4 エンディング分岐

- **論破成功 (`success`)**
  - 正しい犯人選択 + 重要証拠3点 (`log`, `pr`, `spec`) を所持
- **証拠不足 (`warning`)**
  - 犯人選択は正しいが、重要証拠が不足
- **反論失敗 (`failure`)**
  - 犯人選択が不正解

## 3. システム仕様

### 3.1 状態管理

ゲームは以下の状態を持つ。

- `chapter`: 現在チャプター（1〜3、裁判）
- `trust`: 信頼度（選択に応じて増減）
- `evidence`: 取得した証拠キー集合（`Set<EvidenceKey>`）

### 3.2 証拠データ（Evidence）

証拠キーは以下。

- `log`
- `pr`
- `spec`
- `test`

判定上の**重要証拠**は `log`, `pr`, `spec` の3点。

### 3.3 進行ルール

1. チャプターごとに選択肢を表示
2. 選択で信頼度と証拠を更新
3. チャプター3終了後に裁判フェーズへ移行
4. 犯人候補選択後、`judgeOutcome` により結果を確定

### 3.4 判定ロジック

`src/gameLogic.ts` の責務:

- `hasCriticalEvidence(evidence)`
  - `log`, `pr`, `spec` が揃っているかを真偽値で返す
- `judgeOutcome({ suspectIsCorrect, evidence })`
  - 不正解なら `failure`
  - 正解かつ重要証拠ありなら `success`
  - 正解だが重要証拠不足なら `warning`

### 3.5 テスト方針

`src/__tests__/gameLogic.test.ts` では以下を検証する。

- 重要証拠判定の正負ケース
- 犯人不正解時の `failure`
- 犯人正解かつ証拠不足時の `warning`
- 犯人正解かつ証拠十分時の `success`
